# 試算表欄位規格

執行一次 `setup` 之後，這 10 個分頁會自動建好。這份文件是給你「想直接開試算表看資料」時用的。

試算表下方的**頁籤名稱**與第一列的**表頭**都是中文（例如頁籤「帳號」、表頭「帳號編號」）；
下面表格裡的英文是**程式碼裡的欄位／分頁名稱**，中文則對應到試算表上實際看到的文字，
兩者一起列出方便對照。每一節的標題就是「程式碼名稱 — 頁籤名稱」，例如 `Users — 帳號`。

> 如果你的試算表是舊版程式碼建立的（頁籤名稱還是英文的 `Users`、`Machines` 那種），
> 重新執行一次 `setup` 就會自動把頁籤改名成中文，**不會動到任何一筆既有資料**——
> 純粹是分頁改名，資料原封不動留在原本的分頁裡。

> ⚠️ **可以看，盡量不要手改。**
> 系統寫入時會做一致性檢查（金額、權限、快照），手動改容易改出對不起來的帳。
> 真的要改，先想清楚下面每一欄的意思。

---

## Users — 帳號

| 欄位 | 說明 |
|---|---|
| `user_id`（帳號編號） | 系統產生，不要改 |
| `username`（帳號） | 登入帳號，英數字與 `_ . -`，3~20 字 |
| `display_name`（顯示名稱） | 畫面上顯示的名字 |
| `password_hash`（密碼雜湊） | 密碼雜湊（salt + pepper 迭代 SHA-256 一千次）。**看不出原始密碼，也改不回去** |
| `salt`（密碼鹽） | 每個帳號各自的隨機值 |
| `role`（角色） | `admin` 管理員／`patrol` 巡邏人員／`owner` 台主 |
| `status`（狀態） | `active` 啟用／`disabled` 停用 |
| `created_at`（建立時間） / `last_login_at`（最後登入時間） | ISO 時間字串 |

改密碼請走系統管理頁，不要手動改這裡的欄位。

## Machines — 機台

| 欄位 | 說明 |
|---|---|
| `machine_id`（機台編號） | 系統產生，不要改 |
| `name`（名稱） | 機台名稱 |
| `location`（位置） | 位置說明 |
| `status`（狀態） | `running` 營運中／`maintenance` 維修中／`offline` 停機 |
| `color`（顏色） | 機身顏色，`#RRGGBB` |
| `sort_order`（排序） | 首頁排序，數字小的在前 |
| `note`（備註） | 備註 |
| `category`（分類） | `dice` 骰台／`electronic` 電子。**只在新增機台當下決定，之後不能改**——換分類會讓這台過去的紀錄類型（入幣/出幣/活動 或 開分/洗分）跟新分類對不上。空白（這個功能上線前建立的機台）一律當骰台。 |
| `icon`（圖案） | 機台卡片的像素風圖案款式：`classic` 經典／`round` 圓頂／`twin` 雙爪／`tall` 招牌／`dice` 骰子／`sixdice` 六點骰。跟顏色一樣可以隨時在編輯機台時改，不像分類會被鎖住。空白或不認得的值一律當 `classic`。 |
| `carry_in`／`carry_out`／`carry_prize`／`carry_chip_in`／`carry_chip_out`（封存前累計入幣/出幣/活動/開分/洗分） | **不要手動改。** 每次自動封存（見下方「按季自動封存舊資料」）會把當時要搬去封存分頁的那批紀錄加總進這幾欄，首頁 dashboard 每台機台的歷史全部累加＝這幾欄＋目前還留在「紀錄」分頁的量，這樣封存之後這個數字才不會憑空掉下去。機台詳細頁顯示的「累計淨收益」是本週（週日到今天），不會用到這幾欄。 |

## Records — 所有帳目（最重要的一張表）

| 欄位 | 說明 |
|---|---|
| `record_id`（紀錄編號） | 系統產生 |
| `machine_id`（機台編號） | 對應 Machines |
| `type`（類型） | 骰台機台：`in` 入幣／`out` 出幣／`prize` 活動（畫面上叫「活動」，這個內部值沒有改）。電子機台：`chip_in` 開分／`chip_out` 洗分 |
| `amount`（金額） | 金額。活動的話 = `unit_amount × count`；入幣的話 = `(meter_end − meter_start) × 費率`；開分/洗分是手動輸入的金額 |
| `prize_id`（獎型編號） | 活動才有，對應 Prizes |
| `prize_name`（獎型名稱） | **活動登錄當下的獎型名稱快照** |
| `unit_amount`（單價） | **活動登錄當下的單價快照** |
| `count`（次數） | 活動次數 |
| `user_id`（操作人編號） | 誰記的 |
| `created_at`（建立時間） | ISO 時間字串 |
| `voided`（已作廢） | `TRUE` 表示已作廢，所有統計都會跳過 |
| `voided_by`（作廢人） / `voided_at`（作廢時間） | 誰在什麼時候作廢的 |
| `client_token`（防重複權杖） | 防重複送出用；同一個 token 只會寫入一次 |
| `meter_start`（上班表） | 入幣才有：登錄當下的上班表讀數 |
| `meter_end`（下班表） | 入幣才有：登錄當下的下班表讀數 |
| `business_date`（營業日期） | 這筆帳算進哪一天，見下方「營業日」說明 |

> `meter_start`／`meter_end`／`business_date` 都放在**最後幾欄**，不是照邏輯順序排——
> 這幾欄是陸續才加的，新欄位一律加在最後面，不能插進中間。中間插入會讓
> 「這幾欄還不存在時」就已經寫入的舊紀錄，從那一欄開始全部被讀到錯的欄位
> （操作人被讀成碼表讀數、建立時間被讀成備註…一路錯位下去）。系統會在
> 執行 `setup` 時自動偵測並修回被錯位過的紀錄，你不用手動處理。

**為什麼要存快照？**
如果報表是即時去 Prizes 表查單價，那你哪天把「大娃」從 150 改成 200，
上個月的帳會跟著一起變，對帳就再也對不起來了。
存快照之後，改價只影響之後的紀錄，歷史帳永遠不動。
入幣的 `meter_start`/`meter_end` 也是同樣的道理：日後改了每格金額的費率，
舊紀錄的金額不會跟著變，因為金額本身已經算好存下來了，不是每次report都重算。

**收益怎麼算**
```
骰台淨收益 = SUM(入幣) − SUM(出幣) − SUM(活動)　電子淨額 = SUM(開分) − SUM(洗分)　（只算 voided 不是 TRUE 的）
```

**紀錄不會被刪除**，只會標記 `voided`。要查「誰在什麼時候作廢了什麼」，看這三欄。

## Prizes — 獎型

| 欄位 | 說明 |
|---|---|
| `prize_id`（獎型編號） | 系統產生 |
| `machine_id`（機台編號） | **空白 = 全局**（所有機台共用）；填了機台 id = 那一台專屬 |
| `name`（名稱） | 獎型名稱 |
| `amount`（金額） | 單價（成本） |
| `sort_order`（排序） | 活動面板的排列順序 |
| `active`（啟用中） | `FALSE` 表示已停用，不再出現在活動面板，但歷史帳仍算得出來 |

## QuickAmounts — 快捷金額

| 欄位 | 說明 |
|---|---|
| `qa_id`（快捷編號） | 系統產生 |
| `machine_id`（機台編號） | **空白 = 全局**；填了 = 那一台專屬 |
| `type`（類型） | 只會是 `out` 出幣——入幣已改用碼表登錄（見下方 MeterRates），不再用快捷金額 |
| `amount`（金額） | 金額 |
| `label`（顯示文字） | 按鈕上的字，留空就顯示金額 |
| `sort_order`（排序） | 排列順序 |

> 舊資料如果還留著 `type = in` 的列（改版前建立的），不會被自動清掉，
> 但畫面上已經不會再用到，留著也無妨。

## MeterRates — 入幣碼表費率

| 欄位 | 說明 |
|---|---|
| `rate_id`（設定編號） | 系統產生 |
| `machine_id`（機台編號） | **空白 = 全局**；填了 = 那一台專屬 |
| `rate`（每格金額） | 入幣金額 = `(下班表 − 上班表) × rate` |

跟 `QuickAmounts`／`Prizes` 一樣是「全局預設 + 單台可覆寫」，但這裡永遠只有一列
（一個數字，不是一份清單）：改全局就是編輯 `machine_id` 空白的那一列；
「改成本台自訂」是複製一份成該機台專屬；「改回沿用全局」就是把那一列刪掉。

## BizDays — 營業日

| 欄位 | 說明 |
|---|---|
| `biz_id`（營業日編號） | 系統產生 |
| `business_date`（營業日期） | 按下「今日營業開始」當下的日期，這一整個營業日的帳都算進這一天 |
| `opened_at`（開始時間） / `opened_by`（開始人） | 誰在什麼時候按了「今日營業開始」 |
| `closed_at`（結束時間） / `closed_by`（結束人） | 誰在什麼時候按了「今日營業結單」（還在營業中就是空的） |
| `auto_closed`（自動結單） | `TRUE` 表示不是手動結的，是忘記結單、隔天又按「開始」時系統自動幫忙結掉的 |

**這個功能預設不影響任何人。** 首頁一直都是「今天」自動在凌晨 0 點換日，
沒人按過「今日營業開始／結單」的話，行為完全不變。只有店家實際會開到
隔天凌晨、想把整晚的營業額算成同一天時，才需要用這兩顆按鈕。

**同一時間最多只有一筆「進行中」**（`closed_at` 是空的）。按「今日營業開始」時，
如果前一筆還沒結單，系統會自動幫你結掉（標記 `auto_closed`），不會擋住不讓開新的——
現場常常忘記按結單，擋住比自動處理風險更高。

**記帳當下就會把 `business_date` 快照進 `Records`**，之後這筆帳永遠算在那一天，
不會因為之後又開了新的營業日、或系統設定變動而改變。首頁「今日」、機台詳細頁
「今日」、報表的日/週/月分組、CSV 的日期欄，全部照這個欄位算，不是照 `created_at`
的行事曆日期——這樣晚上開到隔天凌晨的營業額才不會被行事曆日期從中間切開。

## DailyLedger — 每日手動帳目

| 欄位 | 說明 |
|---|---|
| `ledger_id`（帳目編號） | 系統產生 |
| `business_date`（營業日期） | 這組數字屬於哪個日期 |
| `turnover`（週轉金） / `transport`（運拿） / `returned_to_house`（還內場） | 整間店當天的現金調度，跟哪一台機台無關。**可以是負數**（例如運拿本來就是現金流出），系統原封不動存起來，不會另外套正負號 |
| `given_to_owner`（台主給，舊） / `taken_by_owner`（台主領，舊） | 這功能剛上線時的單一數字欄位，只保留給**這功能上線前存的舊資料**讀取用——新的寫入一律清空這兩欄，改用下面的 `*_items` |
| `given_to_owner_items`（台主給明細） / `taken_by_owner_items`（台主領明細） | JSON 陣列字串，格式 `[{"name":"老王","amount":5000}, ...]`——台主給／台主領可能不只一位台主，各自可以命名，每次「設定今日數字」是整份覆蓋（同一個 session 裡重存會蓋掉上一次的清單，不是疊加）。金額是 0（含沒填）的項目存檔時就不會留在清單裡 |
| `manual_432`（手動活動支出432） / `manual_441`（手動活動支出441） | 系統自動算出來的「今日432活動金額」之外，另外辦活動時手動填的支出，跟自動算的分開各自扣一次 |
| `updated_by`（更新人） / `updated_at`（更新時間） | 誰在什麼時候最後存過這一天的數字 |
| `biz_id`（所屬營業日編號） | 這組數字屬於哪一個「營業日 session」（`BizDays` 的 `biz_id`），沒有進行中的營業日時是空字串 |

**同一個「營業日 session」裡重新儲存是覆蓋，不是疊加。** 跟 `Records`（可以一直往下加
很多筆）不一樣，這五項比較像「餘額設定」——這個 session 還沒設定過就當全部是 0，
管理員或巡邏人員在首頁「加總」分頁按「✎ 設定今日數字」存一次，這個 session 都用那組
數字，改天要調整就直接覆寫同一列，不會累加出兩倍的數字。

按一次「今日營業開始」就是開一個新的 session（`biz_id` 換一個），這五項會跟著看起來
歸零——**只是「這個 session 找不到自己的列」而已，舊 session 存過的那一列完全沒有
被刪除或改動**，同一個 `business_date` 底下可能同時留著好幾個 session 各自的一列，
都能在試算表裡查得到。首頁「今日」機台卡片、機台詳細頁「今日」數字也是同一套邏輯：
只算「這次營業開始之後」才寫入的紀錄，同一天裡「這次開始之前」記過的帳（不管是忘記
結單被自動結掉的上一個 session，還是這個功能上線前用行事曆日期退回路徑記的）都不會
被算進「今日」，但紀錄本身完全沒被動過，機台詳細頁的「累計」跟報表都還看得到完整歷史。

**按「今日營業結單」之後，「今日」的邊界不會立刻消失。** 結單只是把這個 session
標記結束，並不會讓「今日」退回去跟結單前的舊帳（前面說的「上一個 session」）混在
一起——後端找「今日」邊界時，優先用進行中的 session；沒有進行中的就找「今天結束的
最後一個」繼續沿用它的邊界，直到下次又按「今日營業開始」開新的 session，邊界才會
再往前挪。也就是說結單後看到的「今日」數字，就是剛剛那個 session 的最終結算結果，
不會因為結單這個動作本身而改變。只有「今天完全沒按過這個功能」（今天連一筆 `BizDays`
紀錄都沒有）才會真的退回這個功能上線前的行為：單純比對日期，整個行事曆日一起算。

首頁「加總」分頁的「今日現金結餘明細」就是拿這幾項，加上今日入幣、出幣、
今日432活動金額、電子機台淨贏，一起算出「總結餘」：

```
總結餘 = 入幣 − 出幣 − 今日432活動金額 − 手動活動支出432 − 手動活動支出441
        + 週轉金 + 運拿 + 台主給（明細總和） + 電子淨贏 + 台主領（明細總和） + 還內場
```

「開銷+432獎」這一行顯示的是系統自動算出來的 432 活動金額；「432(手動)」「441(手動)」
是另外兩行，給自動算的之外、另外辦活動時手動填的支出，兩邊分開扣，不會互相取代。
台主給／台主領在畫面上是逐筆列出（用各自的自訂名字當標籤），不是只顯示一個總和數字，
沒有任何一筆時退回顯示「台主給／台主領 $0」這一行占位。

### 「全局預設 + 單台覆寫」怎麼運作

`Prizes`、`QuickAmounts`、`MeterRates` 都用同一套規則：

```
要查某台機台的設定時：
  先找 machine_id = 那台機台 的資料列
    → 有的話，就用這些（完全取代全局，不會合併）
    → 一列都沒有，才回頭用 machine_id 空白的全局設定
```

所以「某台改成自訂」實際上就是把全局那幾列複製一份、把 `machine_id` 填上該機台；
「改回沿用全局」就是把那幾列刪掉。App 裡的按鈕就是在做這兩件事。

## Permissions — 台主授權

| 欄位 | 說明 |
|---|---|
| `user_id`（帳號編號） | 台主的帳號 |
| `machine_id`（機台編號） | 授權他看的機台 |
| `granted_by`（授權人） / `granted_at`（授權時間） | 誰在什麼時候授權的 |

**這張表只對台主有意義。** 管理員與巡邏人員一律看得到全部機台，
不會、也不需要在這裡有資料列。有一列 = 那位台主看得到那台。

## Sessions — 登入狀態

| 欄位 | 說明 |
|---|---|
| `token`（登入權杖） | 登入權杖 |
| `user_id`（帳號編號） | 屬於誰 |
| `created_at`（建立時間） | 登入時間 |
| `expires_at`（到期時間） | 到期時間。**這是唯一的判斷依據**，改前端的儲存內容沒有用 |
| `remember`（記住我） | `TRUE` = 勾了記住我（7 天固定到期）／`FALSE` = 12 小時滑動延展 |

手機掉了想強制登出：把該帳號的列刪掉即可。

## Config — 系統設定

`key`（設定鍵） / `value`（設定值） 兩欄的雜項設定。

| key | 說明 |
|---|---|
| `last_archived_quarter` | 自動封存（見下方）最後封存到哪一季，例如 `2026Q2`。**不要手動改**——報表／匯出對帳表 用這個判斷選到的區間是不是已經被封存走了。 |
| `last_archived_at` | 最後一次自動封存執行的時間（ISO 字串），純參考用。 |

> 密碼用的 pepper **不在這裡**，存在 Apps Script 的「指令碼屬性」`PEPPER`。
> 不要動它——換掉的話所有現有密碼都會失效。

## 按季自動封存舊資料

每次操作（首頁、機台詳細頁、報表、匯出對帳表）都會把整張「紀錄」分頁全部讀進記憶體再篩選，
所以效能是跟著「紀錄」分頁的**累計總筆數**變慢，不是跟著你查詢的區間大小。為了不讓這張表
無限長大，系統會**每月自動檢查一次**（執行過一次 `setup` 之後就會裝好這個檢查，不用手動設定），
把「目前這一季」以前、還留在「紀錄」分頁的資料搬到獨立的封存分頁，例如：

- `封存_2026Q1`（2026 年第一季，1~3 月）
- `封存_2026Q2`（2026 年第二季，4~6 月）

封存分頁的欄位結構跟「紀錄」完全一樣，資料**沒有被刪除**，只是搬到別的分頁，讓「紀錄」
分頁只留最近這一季，讀取速度不會隨著開店年數一直往上疊加。

**幾件事要知道：**

- 首頁 dashboard 每台機台的歷史全部加總不會因為封存而掉下去——封存當下會先把那批
  紀錄的加總記到 Machines 分頁的 `carry_in` 等五欄，之後這個全部歷史的加總＝這五欄＋
  還留在「紀錄」分頁的量。機台詳細頁顯示的「累計淨收益」是本週（週日到今天），只讀
  目前這一季的「紀錄」分頁，不會用到這五欄，也不會被封存動到。
- 報表／匯出對帳表 目前**不會**跨分頁合併查詢。自訂區間如果選到已經封存的舊季度，系統會
  直接明確報錯，告訴你要去哪個封存分頁看，不會默默算出不完整的數字。
- 想確認封存有沒有正常運作：看 Config 分頁的 `last_archived_quarter`／`last_archived_at`，
  或直接到 GAS 編輯器手動執行一次 `archiveOldRecords()`（天生冪等，沒有東西可封存時安全地
  什麼都不做）。

## 跨執行快取（CacheService）

封存解決的是「表越長越慢」，這裡解決的是另一件事：短時間內同一張表被
重複讀好幾次（多個使用者同時開 App、同一人手機背景輪詢）時，每一次都是
全新的 GAS 執行、都要真的打一次 Sheets API 讀整張表——即使兩次讀取中間
資料根本沒變。`dbReadAll()`（`Db.gs`）在讀完一張表之後，會把結果也寫進
`CacheService.getScriptCache()`（GAS 內建、跨執行共用），最多快取 5 分鐘；
下一次不管是誰、從哪個請求進來，只要在這 5 分鐘內又讀同一張表，直接吃
這份快取，不用再打一次 Sheets API。

正確性不是靠這 5 分鐘等它自然過期，而是靠**主動失效**：`dbInsertMany`／
`dbUpdate`／`dbDeleteRows`（以及少數繞過這幾支、直接改儲存格的修復函式，
例如 `_fixTextColumnFormatting()`）寫入的當下，就會立刻把那張表的快取
砍掉——因為 CacheService 是全 script 共用，不是只有自己這次執行看得到，
砍掉之後**所有人**下一次讀都會直接 miss、重新讀到最新資料。5 分鐘只是
防呆用的安全網，不是拿它保證資料新鮮。

`Sessions`／`Users` 這兩張表刻意不進這層快取——登入驗證、登出、改密碼
要求立刻生效，不能有任何一段快取窗口讓已經失效的 token／舊密碼還能通過
驗證；這兩張表資料量本來就很小，不快取也不會慢。

`Records` 也刻意不進這層快取，理由不一樣：這張表是全系統寫入最頻繁的
一張，而且幾乎每次寫入後緊接著就要重讀（入幣/出幣/開獎送出後，回應要
附上最新的機台詳細頁資料）——快取在這張表上幾乎沒機會被別的請求命中
就先被自己下一次的寫入砍掉，等於白白多付一次序列化整張表＋寫進
CacheService 的成本，卻換不到讀取加速，反而讓「送出」這個動作變慢。
這張表通常也是資料量最大的一張，序列化成本最貴，是這幾張表裡投資
報酬率最差的一個。
